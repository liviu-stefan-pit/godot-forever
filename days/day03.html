Concepts you need first

The plan: three small scenes, one Main scene

This game is the official "Dodge the Creeps" tutorial, made portrait-shaped and extended. Godot's scene system means every kind of thing in the game gets its own scene file that you can build and test in isolation, and then instance (like a prefab) into a bigger scene. Today's scenes:

player.tscn
Player (Area2D)                 [player.gd]
├── AnimatedSprite2D            (animations: walk, up)
└── CollisionShape2D            (CapsuleShape2D)

mob.tscn
Mob (RigidBody2D)               [mob.gd]
├── AnimatedSprite2D            (animations: fly, swim, walk)
├── CollisionShape2D            (CapsuleShape2D, rotated 90°)
└── VisibleOnScreenNotifier2D

main.tscn
Main (Node)                     [main.gd]
├── Player                      (instance of player.tscn)
├── MobTimer (Timer)
├── ScoreTimer (Timer)
├── StartTimer (Timer)
├── StartPosition (Marker2D)
└── MobPath (Path2D)
    └── MobSpawnLocation (PathFollow2D)

Tomorrow (Day 4) adds a HUD scene, juice and saving. The names above are fixed for the whole game: scripts refer to nodes by name ($MobPath/MobSpawnLocation), so a typo in a node name is a runtime error, not a cosmetic one.

Why these three node types?

  • Player = Area2D. An Area2D detects overlaps but never pushes or gets pushed. We move it ourselves with position += velocity * delta and ask it "did a body enter you?" via the body_entered signal. For a game where touching an enemy simply ends the run, that is the simplest tool. (Official tutorials point out that CharacterBody2D is the better choice for most real characters that must slide along walls: you will use it on Day 5.)
  • Mob = RigidBody2D. A rigid body is simulated by the physics engine. We give it a linear_velocity once, set gravity_scale to 0, and it keeps flying in a straight line. It is also a body, which is what the player's body_entered signal reports.
  • Main = plain Node. It has no position or look of its own; it only runs game logic and owns the timers. Using Node instead of Node2D communicates "this is a manager, not a thing you can see".
Coming from Unity/Unreal?

A scene is a prefab and a level at the same time. An Area2D + CollisionShape2D is the equivalent of a Collider with "Is Trigger" ticked. A Godot signal is like a C# event / UnityEvent, but it is a first-class part of every node. Timer is a node you drop in the scene instead of writing a coroutine or a Tick function.

Mini lesson 1: collision layers and masks

Every physics object in Godot (anything that extends CollisionObject2D: Area2D, RigidBody2D, CharacterBody2D, StaticBody2D...) has two 32-bit fields, shown in the Inspector under Collision as two grids of checkboxes:

  • Layer (collision_layer): the layers this object lives in. "What am I?" Default: layer 1.
  • Mask (collision_mask): the layers this object looks at. "What do I care about?" Default: layer 1.

The rule: object A notices object B only if B's layer is ticked in A's mask. It is one-directional. A body and an area follow it independently, which is why you can build "the player sees enemies but enemies ignore the player" setups. Layers do not have meaning on their own: you give them names (Project > Project Settings > Layer Names > 2D Physics), and today you name the first three.

Layer #NameBit valueWho lives here in Dodger
1world1Nothing yet (walls/floors in later games; this is also the default layer of every new object, which is why we move things off it)
2player2Player
3enemies4every Mob

And who looks at whom:

ObjectLayer (lives in)Mask (looks at)Result
Player (Area2D)2 player3 enemiesReports body_entered when a mob overlaps it
Mob (RigidBody2D)3 enemiesnone (all unchecked)Collides with nothing, so mobs never bump each other and pass straight through everything

In code the same idea reads set_collision_layer_value(2, true) and set_collision_mask_value(3, true) (layer numbers start at 1), or you can assign the raw bit field, collision_layer = 2, collision_mask = 4. Today you tick the checkboxes; later games set them in code when they spawn projectiles.

Docs: the official variant

The official tutorial leaves everything on layer 1 and only unchecks mask 1 on the mob so mobs ignore each other. That works for a two-object game, but it stops scaling the moment you add a third kind of object. Naming layers from the first game is a habit worth building. Read Physics introduction > Collision layers and masks after today's build.

Coming from Unity?

Unity has one global Layer Collision Matrix. Godot stores the matrix per object (layer + mask). More flexible, a little more to set up, and a common source of "why doesn't my bullet hit anything" bugs: if collisions are not happening, check the layer/mask pair first.

Mini lesson 2: Path2D and PathFollow2D

We want mobs to appear at a random point on the border of the screen and fly inwards. Rather than computing four edges by hand, we draw the border as a path once, in the editor:

  • Path2D stores a Curve2D: an ordered list of points (optionally with Bézier handles). It draws the curve in the editor and nothing else.
  • PathFollow2D is a child of a Path2D. Set its progress (distance in pixels along the curve) or progress_ratio (0.0 = start, 1.0 = end) and it positions itself on the curve. With its rotates property on (the default) it also turns to face the direction the curve is travelling in at that point.
  • So spawn.progress_ratio = randf() picks a uniformly random point on the whole perimeter, and spawn.rotation tells us which way the border runs there.

The path has four points, one per screen corner, and it must be drawn clockwise (on screen, with Y pointing down):

  P1 (0,0) ──────────► P2 (480,0)
     ▲                      │
     │      clockwise       ▼
  P4 (0,720) ◄──────── P3 (480,720)

  Along the top edge the path travels to the right  -> rotation = 0
  Rotating 90° (PI / 2) clockwise points it DOWN     -> into the screen.
  Along the right edge the path travels down         -> rotation = PI / 2
  Adding PI / 2 again points it LEFT                 -> into the screen.

That is the trick in main.gd: direction = spawn.rotation + PI / 2.0 is "perpendicular to the border, pointing inward" for every edge. If you draw the path counter-clockwise, the same formula points outward and every mob flies off-screen the moment it spawns. We then add a random wobble of ±45° (PI / 4) so the creeps do not all arrive in perfectly straight lines. Godot angles are in radians; PI is a half turn and TAU a full turn.

Your code asks for the action and never for a specific key, which is what makes remapping and gamepad support free later. You did this on Day 2; here it is again as steps because the Dodger needs exactly these four names.

player.gd

Now the script. A few decisions in the listing, so they do not surprise you:

  • Input.get_vector("move_left", "move_right", "move_up", "move_down") returns the movement direction as one Vector2 from your four actions. It replaces four if checks and the normalization: diagonal keyboard input gives a vector of length 1, so moving diagonally is not faster. (The manual version is in the box below the listing; read it once so you know what the function does for you.)
  • The script uses _process, not _physics_process: an Area2D has no physics integration to keep in sync, so we move it once per rendered frame, multiplied by delta (the time since the last frame) so speed does not depend on frame rate.
  • position.clamp(Vector2.ZERO, screen_size) keeps the center of the player inside the window rectangle.
  • class_name Player registers a global type so main.gd can write var player: Player and get typed autocomplete.
  • The hit signal is custom: the Player announces "I got hit" and does not know or care who listens. Main will listen.
  • The collision shape is switched off with set_deferred, never directly. The physics engine is busy calling _on_body_entered; changing physics state in the middle of that callback is not allowed, and set_deferred says "do it at the end of this frame".
  1. Attach a script. In the Scene dock right-click Player and choose Attach Script. In the Attach Node Script dialog leave Language = GDScript and the template as it is. Set Path to res://player.gd and click Create. The editor jumps to the Script workspace with a new file open.
  2. Replace the whole file. Click inside the code, press Ctrl+A to select everything, and paste this listing over it. Then press Ctrl+S.
  3. Go back to the 2D workspace. Click 2D in the Workspace buttons (top center).
  4. Check the exported property. Select Player in the Scene dock. The Inspector now shows a Player section with Speed = 400. Changing it here would override the script default for this scene only.
What Input.get_vector() replaces (manual version, for reference only)

Do not type this: it is what the single get_vector line does for you.

Normalizing means "keep the direction, set the length to 1", then you multiply by speed. get_vector additionally supports analog sticks (partial tilt = partial speed), which matters when you add gamepad support.

Your first signal connection (do it the editor way)

The player must be told when a mob touches it. Area2D has a built-in body_entered(body) signal that fires when a physics body enters the area. We connect that signal to the function _on_body_entered in player.gd. There are two equivalent ways to connect a signal; today you see both.

  1. Select the emitter. In the Scene dock click Player.
  2. Open the signal list. In the dock on the right, next to the Inspector tab, click the Node tab, then its Signals sub-tab. You see the signals of Player grouped by class: your custom hit() at the top (the script declared it) and the Area2D signals such as body_entered(body: Node2D) below.
  3. Connect. Double-click body_entered(body: Node2D). The Connect a Signal dialog opens. The receiver is Player itself and the Receiver Method is already _on_body_entered, which is the function you pasted. Leave everything else as it is and click Connect.
  4. See the result. In the Signals list the entry now has a small green connection icon on the right. Open player.gd (Script workspace): a green arrow icon sits in the left gutter next to func _on_body_entered. Because the function already existed, Godot only registered the link; if it had not existed, Godot would have created an empty one for you.
The code way (signal connection #1 of 3 explained both ways)

The same connection written in code goes in _ready():

The editor way stores the link in the .tscn file and shows it in the Signals list; the code way is easier to search and diff, and you need it for nodes that you create in code. Never do both for the same signal and function: Godot prints "Signal 'body_entered' is already connected" and the function would run twice. Today you use the editor way; from Day 5 on you will use whichever is shorter for the situation.

  1. Test the Player scene alone. Press F6 (Run Current Scene, top-right Play buttons). A 480x720 window opens. The player sits half-hidden in the top-left corner because the root node is at (0, 0).
  2. Move it. Press the arrow keys (and WASD). The character should move in every direction, never faster diagonally, and never leave the window. Left/right plays walk (mirrored when moving left); up/down plays up (flipped vertically when moving down); standing still freezes the animation. Close the window with F8 or the window's X.
  3. Hide at start. Open player.gd and remove the leading # from the line # hide() in _ready() so it reads hide(). Why: in the real game the player should be invisible until Main calls start(). Press Ctrl+S. (Running the Player scene alone now shows an empty window; that is correct.)

Before step "Hide at start": F6 shows a moving, animated, screen-clamped player and the Output panel (bottom) is empty of red text. If you see Attempt to call function 'play' in base 'null instance', a node name does not match: the scene must contain AnimatedSprite2D and CollisionShape2D spelled exactly so. If nothing moves, an Input Map action is misspelled or the script is attached to the wrong node (the script icon should be next to Player, not a child). If the animation never plays, the animations must be named exactly walk and up.

Block 4: The Mob scene

Mobs are simple: spawn at a screen edge, pick a direction and a speed, fly straight, delete yourself once you are off-screen. A RigidBody2D does the "fly straight" part for free once it has a linear_velocity and no gravity.

  1. Create a new scene. Menu bar: Scene > New Scene. A new empty tab opens next to player.tscn above the viewport. In the Scene dock click Other Node, search RigidBody2D, select it, click Create.
  2. Rename and save. Select it, press F2, type Mob, Enter. Press Ctrl+S and save as res://mob.tscn.
  3. Add the three children. With Mob selected press Ctrl+A and add AnimatedSprite2D. Select Mob again and add CollisionShape2D. Select Mob again and add VisibleOnScreenNotifier2D. The tree must be: Mob with the three as direct children (not nested in each other). The notifier will tell us when the mob has left the screen. A common slip is adding a node while a child is selected, which nests it under that child.
  4. Turn off gravity. Select Mob. In the Inspector find Gravity Scale (gravity_scale) in the RigidBody2D section and set it to 0. Without this, every mob would fall to the bottom of the screen like a rock.
  5. Set the mob's collision layer. Still on Mob, open Collision in the Inspector (under CollisionObject2D). In Layer: uncheck 1, check 3 (enemies).
  6. Set the mob's mask. In Mask: uncheck 1 so that no box is ticked. The mob now does not look at anything, so mobs fly through each other and the player's area (which is not a solid body anyway) does the detecting. This is the "don't collide with each other" requirement, solved by the layer/mask table instead of by a special case.
  7. Build the animations. Select AnimatedSprite2D. In the SpriteFrames panel at the bottom rename default to fly. Click Add Animation twice and name the new ones swim and walk.
  8. Fill the frames. For each animation, select it in the list and drag the matching pair of images from art/ into the Animation Frames area: fly gets the two flying frames (enemyFlyingAlt_1, enemyFlyingAlt_2), swim the two swimming frames (enemySwimming_1, enemySwimming_2), walk the two walking frames (enemyWalking_1, enemyWalking_2). Both work. Read it back: the whole loop in one minute

Understanding this flow is more valuable than memorizing any line. When the game starts (or restarts), new_game() resets the score, moves the (hidden) player to StartPosition and shows it, and starts StartTimer. Two seconds later StartTimer.timeout starts MobTimer and ScoreTimer. Every 0.5 s MobTimer.timeout runs _on_mob_timer_timeout(), which instantiates a mob, parks the follower at a random path position, aims the mob inwards and gives it a velocity. Every second ScoreTimer.timeout adds a point. When a mob's body overlaps the player's capsule, Player._on_body_entered() hides the player, emits hit and defers the shape's removal; Main.game_over() stops both timers. A mob that flies off-screen triggers screen_exited and removes itself.

Design note: "call down, signal up"

Notice the direction of communication. Main (the parent) calls methods on its child: _player.start(...). The child Player never reaches up to call Main; it emits a signal and whoever cares connects. That one rule keeps scenes reusable and testable on their own (you ran player.tscn and mob.tscn alone with F6 today, and nothing broke because they do not depend on Main).

Common pitfalls

  • Pressing F5/F6 with unsaved scenes. Godot normally saves for you when you run, but a script edited in the Script workspace and not saved, or a scene tab with a (*) in its title, is a classic reason for "my change does nothing". Ctrl+S in the right place.
  • A node name that does not match $Path. If you rename AnimatedSprite2D, MobTimer or StartPosition in the Scene dock, $AnimatedSprite2D/$MobTimer/$StartPosition become null and the game crashes with "Invalid access" or "on a null value". The editor will not warn you. Rename the node back, or change both.
  • Adding a node to the wrong parent. New nodes become children of whatever is selected. If you added CollisionShape2D while AnimatedSprite2D was selected, it is nested under the sprite and gets scaled by 0.5. Drag it in the Scene dock back onto Player.
  • Collision layer and mask mismatch. Mobs that pass through the player without effect: the player's Mask must include 3 and the mob's Layer must be 3. A mob that bounces off nothing but also never reports: the same pair. Rule of thumb: when a collision does not happen, open both objects' Collision grids and read them out loud as sentences ("The player looks at layer 3; the mob lives on layer 3").
  • Disabling the collision shape directly inside the callback. _shape.disabled = true inside _on_body_entered can produce "Can't change this state while flushing queries" errors. Use set_deferred("disabled", true).
  • The path drawn counter-clockwise. Mobs fly away from the play field immediately. The code is right; the path direction is wrong.
  • Connecting a signal twice. Using the Node tab and .connect() in code for the same signal and function. Symptom: an error "already connected" or a handler running twice (score +2 per second).
  • Tabs in a script. If you paste a listing and the editor shows "Mixed use of tabs and spaces" or the indentation looks wrong, check Editor > Editor Settings > Text Editor > Behavior > Indent > Type is Spaces. Select the file contents and use Edit > Convert Indent to Spaces in the Script workspace (Edit menu above the code).
  • Forgetting to set the main scene. F5 asks which scene to run; picking the wrong one (for example player.tscn) gives an empty window. Right-click main.tscn > Set As Main Scene.

Challenge (optional, 20-30 min)

Make the creeps vary, and make the game fairer

Do any two of these. Only build on top of the Day 3 end state, and save a copy of the project folder first so you can restore it before Day 4 (Day 4 assumes the listings on this page).

  • Random size. Each spawned mob gets a random scale between 0.8 and 1.3 so the swarm is not uniform. Hint: in _on_mob_timer_timeout() set mob.scale = Vector2.ONE * randf_range(0.8, 1.3) before add_child(mob). Scaling the root scales its collision shape and sprite together, which is why this is easier than scaling only the sprite. Check with Debug > Visible Collision Shapes that the hitboxes grew too.
  • Invulnerability grace. The player should not die in the first 0.5 s after start(). Hint: keep _shape.disabled = true for 0.5 s using await get_tree().create_timer(0.5).timeout inside start(), then set it to false; make sure set_deferred is used where the physics callback is involved.
  • Edge-biased spawning. Spawn twice as many mobs from the top than from the sides. Hint: progress_ratio maps the whole perimeter (the top edge is the first 480 of 1800 pixels, about 0.27 of it). Think about how to pick the ratio from a weighted range.
  • Debug text. Print how many mobs are alive every second with get_child_count() and confirm the number stays bounded (proof that screen_exited cleanup works).

Check yourself

The player's Area2D has Layer = 2 and Mask = 3. A mob has Layer = 3 and an empty Mask. What happens when they overlap?

  • Nothing: both need the other's layer in their mask
  • The player's body_entered fires; the mob does not react to the player
  • Both fire their signals
  • The mob is pushed away by the player

Detection is one-directional: object A notices B when B's layer is in A's mask. The player's mask contains 3 (the mob's layer), so it notices the mob. The mob's mask is empty, so it notices nothing, which is also why mobs pass through each other.

Why does _on_body_entered use _shape.set_deferred("disabled", true) rather than _shape.disabled = true?

  • Because disabled is a read-only property
  • To make the shape disappear one second later for a visual effect
  • Because physics state cannot be changed while the engine is in the middle of processing collisions; deferring runs it safely at the end of the frame
  • Because it makes the signal fire only once per mob

The callback runs inside the physics step. Changing monitoring or shape state there is unsafe, so set_deferred() queues the change for a safe moment. The effect (no more hits after the first) is a side effect of disabling the shape, not the reason for deferring.

You draw MobPath counter-clockwise by mistake. The spawner code is unchanged (direction = spawn.rotation + PI / 2.0). What do you see?

  • Mobs spawn on the edges but fly outwards, off the screen
  • The game crashes with a null error
  • Nothing changes: PathFollow2D ignores the order of points
  • Mobs spawn only on the top edge

PathFollow2D.rotation follows the direction of travel of the curve. Reversing the order reverses the tangent, so adding PI / 2 (a 90° clockwise turn) now points away from the play field. Same formula, opposite direction.

What does Input.get_vector("move_left", "move_right", "move_up", "move_down") give you for free compared with four is_action_pressed() checks?

  • It makes the player move faster
  • It automatically clamps the position to the screen
  • It plays the correct animation
  • A single direction vector that is already limited to length 1 (so diagonals are not faster) and works with analog sticks

It combines the actions into one Vector2 with a circular dead zone and a maximum length of 1. Clamping to the screen is done separately with position.clamp(), and animation selection is custom code.

A mob script says _sprite.play(mob_types.pick_random()). Where do the names it picks from come from?

  • From a hard-coded list in main.gd
  • From the SpriteFrames resource of the AnimatedSprite2D: get_animation_names() lists the animations you created (fly, swim, walk)
  • From the file names in art/
  • From the Input Map

SpriteFrames is a resource holding named animations. Reading its names at runtime means that adding a fourth animation in the editor makes the mob use it without touching the script.
