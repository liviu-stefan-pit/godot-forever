Concepts you need first

UI in Godot: Control nodes, anchors and containers

Everything in a user interface extends Control: Label, Button, panels, containers. A Control has a rectangle (position + size) and, unlike a Node2D, can be positioned relative to its parent's edges. Godot gives you two layout tools and you mix them:

  • Anchors. Four anchor values (left, top, right, bottom, each 0.0 to 1.0) say which point of the parent's rectangle each edge is pinned to; four offsets say how far from that point. Anchor presets are one-click combinations: Top Wide (pinned to the top edge, stretching across the full width), Bottom Wide, Center, Full Rect (pinned to all four edges). Use them to pin big chunks of UI to screen edges, so the layout survives different window shapes.
  • Containers. A Container node (VBoxContainer, HBoxContainer, MarginContainer, CenterContainer, GridContainer...) owns the position and size of its children and lays them out for you. Inside a container you do not set position or size by hand; you set size flags and minimum size instead. Use containers for everything that flows: a row of labels, a column of buttons, padding.
  • Size flags (Inspector > Layout > Container Sizing, horizontal and vertical): Fill (use the whole slot given to me), Expand (ask the container for the free space; several expanders share it), Shrink Begin/Center/End (when expanded, hug the start, middle or end of the slot).
  • Theme. A Theme resource stores default fonts, font sizes, colors and styleboxes per control type. Controls look for a theme in their parents, then in the project theme (Project Settings > GUI > Theme > Custom). Per-node Theme Overrides in the Inspector beat the theme for just that node.
Rule of thumb

Anchors place the big blocks; containers arrange what is inside them. Today's HUD: a MarginContainer pinned to the top (Top Wide) holds an HBoxContainer with score and best score; a CenterContainer pinned Full Rect centers the message; a MarginContainer pinned Bottom Wide holds a VBoxContainer of buttons.

Coming from Unity/Unreal?

Anchors work like Unity's RectTransform anchors. Containers are Unity's Layout Groups (Vertical/Horizontal Layout Group + Content Size Fitter) and Unreal's Vertical/Horizontal Box and Size Box widgets. A CanvasLayer is a screen-space overlay canvas.

Why a CanvasLayer for the HUD?

A CanvasLayer draws its children on a separate canvas that is not affected by the camera. Today you add a Camera2D and shake it when the player dies; the world shakes, but the score text stays rock-steady because it lives on the HUD's layer. The layer also keeps UI above all gameplay nodes without fighting over draw order.

Tweens in one minute

create_tween() returns a Tween bound to the node. Each tween_property(object, "property", final_value, duration) animates a property from its current value; calls are chained (run one after another) unless you call set_parallel(true). set_trans() and set_ease() shape the curve: Tween.TRANS_BACK with Tween.EASE_OUT overshoots slightly and settles, the classic "pop". A subproperty path such as "modulate:a" animates only the alpha channel. You used tweens on Day 2; today they carry most of the game feel. Do not tween the position or size of a child inside a container: the container owns those. Tween scale and modulate instead, which are free.

Pausing and process modes

Setting get_tree().paused = true stops physics and the processing of every node whose Process > Mode is Pausable, which is what the default Inherit resolves to. Particles, audio streams and tweens bound to paused nodes freeze too. A node (and its children, if they Inherit) set to Always keeps running while paused. That is how a pause menu or the HUD can react to "unpause" while the game below is frozen. Signals still fire on paused nodes.

user:// and saving a best score

res:// is your project, read-only in an exported game. user:// is a per-user writable folder, created automatically. On Windows the default location is %APPDATA%\Godot\app_userdata\<project name>, so for this project %APPDATA%\Godot\app_userdata\g01-dodger. Today you store the best score in a small INI-style file with ConfigFile (sections, keys, load(), save()). ConfigFile keeps integers as integers, which is why it is a good fit for settings and tiny saves; the larger saves of later days use JSON.

What "export" means

Running from the editor uses the editor binary and your res:// files. Exporting packs your resources into a .pck file and pairs it with a prebuilt, trimmed export template runtime (a game executable without the editor). You install templates once per Godot version and create an export preset per platform in Project > Export.... Details are in Block 5.

Version note

The embedded game window and its Game workspace (used in Block 6) exist since Godot 4.4. The Windows icon/product-name step works without extra tools in recent versions; Godot 4.4 and older required a separate tool called rcedit for that (see the note in Block 5). Everything else today works on any Godot 4.3+.

hud.gd

The HUD never knows about mobs, timers or the player. It exposes a small public interface (update_score, update_best, show_message, show_game_over) and two signals (start_game, reset_best_requested). It also owns the pause key, because it is the one node that keeps running while the game is paused. Points to notice:

  • show_game_over() uses await _message_timer.timeout and await get_tree().create_timer(1.0).timeout: the function suspends (without freezing the game) and resumes when the signal fires, so a three-step sequence reads top to bottom.
  • Messages are shown and hidden by animating modulate:a and scale, not by hide()/show(). A hidden control inside a container stops taking space; a transparent one does not, so the layout never jumps.
  • The class keeps a reference to its message tween and kills it before starting another, so quick successive messages never fight over the same property.
  • The Reset button needs two presses ("Really reset?") so a stray click does not wipe the best score.

  3. Connect the Start button (editor way). Select StartButton. Node tab > Signals. Double-click pressed(). In the dialog the receiver is HUD and the method _on_start_button_pressed. Click Connect.

The mobs group

  1. Open the Mob scene. In the FileSystem dock double-click mob.tscn. Select the root node Mob in the Scene dock.
  2. Add it to a group. In the right dock click the Node tab, then the Groups sub-tab (next to Signals). Click the + button; in the Create New Group dialog type mobs and click Add (or OK). The code way

You can also tag a node from code: add_to_group("mobs") in Mob._ready(). The editor way is visible in the Groups tab, which is why we use it here. Do not use both: a node cannot be in the same group twice, so it would simply be redundant.

The save helper

The best score lives in a small script with only static functions, so nothing needs to be instanced or autoloaded: HighScore.load_best() works from anywhere. It extends RefCounted because it never needs to be in the scene tree.

  1. Create the script file. In the FileSystem dock right-click an empty area > New > Script.... In the dialog set Path to res://high_score.gd (any Inherits value is fine, you replace the file) and click Create. Select all and paste: Press Ctrl+S.
Why int(...) around get_value?

get_value() returns a Variant. The cast documents that we expect an integer and makes the function's return type honest. (With JSON saves, which you meet on later days, the cast is essential because JSON stores every number as a float.) ConfigFile itself would keep an int as an int.

Block 4: Juice and game feel

Juice is the small feedback that makes a game feel alive: things pop, shake, fade, sparkle and make noise when something happens. Most of today's juice is already in your scripts; here you add the one remaining visual piece (a particle trail), then tune every feature once so you know exactly which number controls which feeling.

A particle trail behind the player

A GPUParticles2D node emits many tiny sprites ("particles"). It does nothing by itself: it needs a ParticleProcessMaterial that describes how each particle starts and evolves. We want a short, fading dust trail that stays in the world where the player was, so it looks like a trail rather than something glued to the character.

  1. Open the Player scene. Double-click player.tscn in the FileSystem dock. Select the Player root node.
  2. Add the emitter. Press Ctrl+A, search GPUParticles2D, click Create, rename the node Trail. It shows a yellow warning triangle: it still needs a material.
  3. Create the process material. In the Inspector open Process Material and click the empty Material field > New ParticleProcessMaterial. White dots start to fall downwards from the player's center in the viewport; the warning disappears.
  4. Emitter settings. Still on Trail, set Amount to 24 (how many particles exist at once) and Time > Lifetime to 0.5 (seconds each lives). Under Drawing make sure Local Coords is off (local_coords = false, the default). With it off, particles keep their world position after they are born, which is exactly what makes a trail. Turn it on and the particles would follow the player rigidly.
  5. Draw it behind the sprite. Scroll to CanvasItem > Ordering and set Z Index to -1. It is relative to Player, so the trail draws under the sprite but above the Background (Z -10).
  6. Find the material properties fast. The material has dozens of properties. Click the material to expand it and use the Filter Properties box at the top of the Inspector: typing gravity shows only the gravity row, and so on. Set the following one by one:

    Initial Velocity > Velocity Min / Max (initial_velocity_min/max)10 / 40a small random drift so the dust scatters a bit
    Gravity (gravity, a Vector3)0, 0, 0the default pulls particles down; a trail should not fall

Click the new CurveTexture to expand it; if its Curve field is empty, click it and choose New Curve. A small graph appears: the X axis is the particle's age from birth (left) to death (right), the Y axis the multiplier applied to the scale. You want a line from 1.0 at the left to 0.0 at the right. If the graph is empty, left-click once near the top-left corner and once near the bottom-right corner to add two points; if it already shows two points, drag the left point up and the right point down. (Right-click a point to delete it.) The viewport now shows dots that shrink to nothing.
  8. Stop the preview emission. The script will turn emission on and off, so untick Emitting on the Trail node (Inspector, top of the GPUParticles2D section). Save with Ctrl+S.
Optional polish

The material also has an Alpha Curve (alpha_curve) that fades transparency over the particle's life, and a Color Ramp for gradients. Add an Alpha Curve the same way as the Scale Curve for a softer fade. A Texture on the Trail node (for example one of the art images) replaces the squares with sprites.

Now update player.gd: the trail should emit only while the player is moving. The only changes are the new _trail reference and the _trail.emitting line; the file is shown whole so you can replace it in one go.

  1. Replace player.gd. Open it (click the script icon next to Player in the Scene dock), Ctrl+A, paste, Ctrl+S:
  2. Test it. Press F5, start a game, and move around. A cyan, shrinking dust trail is left in your wake; when you stand still it stops emitting and the remaining particles fade out. Tune it: select Trail and change Lifetime to 0.9 for a longer trail, then back to 0.5.

A fading trail follows you, stays where you have been, and appears only while you move. If the particles move with the player as a rigid cloud: Local Coords is on. If you see only a white dot or nothing: check the material is assigned, Scale Min/Max are 5/9 and the scale curve is not flat at 0. If the trail is hidden behind the background: Trail Z Index must be -1 and Background Z Index -10. If the editor reports a null error for $Trail: the node must be named exactly Trail and be a direct child of Player.

Tune the tweens (score pop and messages)

  1. Feel the score pop. In hud.gd, in update_score(), change Vector2(1.4, 1.4) to Vector2(2.0, 2.0) and press F5: a huge bounce on every point. Change it back to 1.4. Two chained tween_property calls (grow, then shrink) run one after another because the tween is sequential by default; Tween.TRANS_BACK with EASE_OUT adds the overshoot.
  2. Feel the message animation. In _pop_in() the tween is set_parallel(true), so the fade-in (modulate:a) and the scale-up run together. Try changing the starting scale Vector2(0.6, 0.6) to Vector2(2.0, 2.0): the text now shrinks into place instead of growing. Revert it.

Screen shake

_shake_camera() in main.gd builds a sequential tween of eight short steps. Each step moves the Camera2D.offset to a random point within a radius that decreases linearly from SHAKE_STRENGTH to zero, and a final step eases back to Vector2.ZERO. Changing offset moves what the camera sees without moving the camera node, so the world appears to shake while the HUD (a CanvasLayer) stays still.

  1. Exaggerate it. Change SHAKE_STRENGTH from 16.0 to 48.0 and die once: a violent shake. Because the Background is 60 px bigger than the window on each side, you never see the edge, even at 48. Set it back to 16.0 (a comfortable value for a 480x720 field).
  2. Why a tween and not _process? A tween needs no state variable, no per-frame timer and cleans itself up. The shake would have taken 10 lines of timer logic otherwise.

Sound

Two AudioStreamPlayer nodes (non-positional audio) do all the work: Music.play() in new_game(), Music.stop() and DeathSound.play() in game_over(). The music loops because of the import setting. Both play on the Master audio bus. Later games add separate Music and SFX buses with volume sliders. For now: play a game, then change the Volume dB of Music in the Inspector to -20 and listen to the mix. Decibels are logarithmic: every -6 dB halves the amplitude. Set it back to -8.

The difficulty ramp

Every second ScoreTimer adds a point and calls _apply_difficulty(). The level is the score divided by five, rounded down. Each level shortens the spawn interval by 0.03 s (never below 0.2 s) and adds 12 px/s to the mob speed (never more than +150). The numbers are constants at the top of main.gd, so balancing the game means editing numbers, not logic.

Pause with Esc

The HUD handles ui_cancel (Esc, a built-in action you did not have to create) in _unhandled_input(). _toggle_pause() flips get_tree().paused and shows Paused. Everything that is Pausable freezes: Main, the player, the mobs, the timers, the Music stream and the particles. The HUD is Always, so it still gets the second Esc press and can unpause. The pause only works while a game is running (_game_active).

  1. Pause mid-game. Press F5, start, and press Esc while creeps are flying: everything freezes, the music pauses, and Paused stays on screen. The player does not move when you press the arrows.
  2. Resume. Press Esc again: the text fades and the game continues from the same state (music resumes mid-track).
  3. Check the guards. On the title screen, Esc does nothing (no game is active). During the "Get Ready" countdown it pauses the start timer too.
Common mistake

Do not set Main's Process > Mode to Always to "make pause work". Its children (timers, the player, every mob) inherit Always and would keep running while the tree is paused. Put the pause logic on a small node that is Always (here the HUD) and leave the game Pausable.

You can: see the trail, feel the score pop and message animations, shake the screen on death, hear music and the death sound, notice mobs getting faster and denser (try RAMP_EVERY = 1 if unsure), see a persistent Best: N that survives restarts, reset it with two clicks, and pause/resume with Esc. If the pause message appears but the game keeps running, a node under Main has Process > Mode = Always; set it back to Inherit. If Esc does nothing, HUD.process_mode must be Always and you must have pressed Start first.

Block 5: First Windows export

Running with F5 uses the editor. An export builds a game people can start without Godot: a small runtime (the export template) plus your resources in a .pck. You install templates once per Godot version, then make one Windows preset for this project.

Install the Windows export templates

  1. Open the template manager. In the Menu bar choose Editor > Manage Export Templates.... The Export Template Manager window opens. It lists platforms you have and have not installed.
  2. Select Windows x86_64. Tick the Windows template whose architecture is x86_64. That is the default in the Windows export docs and the one a normal Windows 11 PC runs. Leave x86_32 and arm64 unticked. Leave ICU Data unticked too: that pack is for emoji and for languages such as Chinese, Japanese and Korean, which this game does not use.
  3. Download them. Click Install Selected Templates and wait until the manager shows that version as installed. The download is large; a progress indicator stays up while it runs. Close the manager when it finishes.
If the manager cannot download

The same window has a button in the upper right that installs templates from a .tpz file. The docs say you can download that archive from the official download page, godotengine.org/download (verify the file name there; it changes with the version). Pick the TPZ that matches your editor version exactly. A TPZ for every platform is the same templates, just larger. External resource: verify on the official page, steps change.

Re-open Editor > Manage Export Templates.... The Windows x86_64 row for your editor version is marked installed. If Install Selected Templates does nothing: no box is ticked, or there is no internet. If a later export says the templates are missing: the installed version does not match the editor (a 4.3 template will not export from a 4.5 editor).

Create the Windows Desktop preset

  1. Open the export dialog. Menu bar: Project > Export.... The dialog is empty until a preset exists. (The export docs also mention an Export button that opens this same dialog.)
  2. Add the preset. Click Add… at the top of the dialog. A platform list opens. Choose Windows Desktop. A preset named Windows Desktop appears in the list on the left, and its options fill the right side. That name is the one the docs pass to --export-release "Windows Desktop".
  3. Set the export path outside the project. On the right, find Export Path and click its folder icon. In the save dialog go to C:\GodotProjects (not inside g01-dodger), create a folder named g01-dodger-export, and save the file as Dodger.exe. The field must end in Dodger.exe. Exporting inside res:// makes the editor try to import the exe.
  4. Check the architecture. In the options, under Binary Format, set Architecture (binary_format/architecture) to x86_64 if it is not already. An arm64 exe will not start on a typical Intel or AMD PC.
If Add… does not say Windows Desktop

The Windows tutorial and the command-line example both use the preset name Windows Desktop. The class reference on the docs master branch describes the same entry as adding a "Windows" preset. If your list shows Windows and not Windows Desktop, choose Windows. Then set the preset's name, shown above its options, to Windows Desktop so the command later on this page matches.

Icon, product name, and Embed PCK

  1. Leave the icon on the project default. Still in the preset, open Application and look at Icon (application/icon). Leave it empty. The docs say an empty icon falls back to the project icon (Project > Project Settings > Application > Config > Icon, application/config/icon), which is already icon.svg. Godot turns that image into the Windows .ico for you. Since Godot 4.1 you do not build an ICO by hand and you do not install a separate tool.
  2. Keep resource editing on. In the same Application group, Modify Resources (application/modify_resources) must stay enabled. When it is on, the exporter writes the icon and the product name into the exe. When it is off, Windows keeps the template's own icon and name.
  3. Set the product name. Set Product Name (application/product_name) to Dodge the Creeps. The property is required. This is the name in the exe's file properties. It does not change user://: that folder follows Application > Config > Name (application/config/name), which is still g01-dodger.
  4. Leave Embed PCK off for this first build. Under Binary Format, leave Embed Pck (binary_format/embed_pck) unticked. Off means the resources are a separate .pck next to the exe, so you can see both files. On means they are stored inside the exe (the docs limit that to about 3.89 GB for the exe and the data together). You will try the ticked version in a minute; do the unticked export first.
About rcedit

The version note at the top of this day mentioned rcedit for changing the exe icon on older editors. The current Windows icon page does not use that tool: from Godot 4.1 the exporter builds the ICO from Application > Icon or from the project icon. If an old editor still pops up a rcedit error, export anyway. The game runs; only the file icon stays the default Godot logo. A hand-made ICO is optional and is documented on the icon page linked at the end.

Release export, then the exe

  1. Export a release build. At the bottom of the dialog, make sure Export With Debug is unchecked. Click Export Project (not Export PCK/ZIP, which writes only the data, and not Export All). If a confirm dialog appears, confirm. Wait until the progress bar finishes, then close the export dialog.
  2. Look at the two files. In Explorer open C:\GodotProjects\g01-dodger-export. You should see Dodger.exe and Dodger.pck side by side. The Windows export page describes this package as a PCK bundled with a trimmed binary (it uses the phrase "data.pck" for that package). With your export path, the file next to the exe is named from the exe: Dodger.pck. Both files have to stay in that folder. Copying only the exe produces a window that cannot load the game.
  3. Run it. Double-click Dodger.exe. The portrait window opens with no editor around it. Click Start, survive a few seconds, die, and confirm Best: updates. Close the window.
  4. Confirm the save is the same folder as in the editor. Press Win+R, paste %APPDATA%\Godot\app_userdata\g01-dodger, and press Enter. dodger.cfg is there, and its best value matches the exe. Then press F5 in the editor: the title already shows that same best score. user:// is per project name, not per "editor vs exe".
Windows SmartScreen

The first time you start your own unsigned exe, Windows may say it protected your PC. That is normal for an export you have not code-signed. Choose More info, then Run anyway. Signing needs a certificate and is covered in the Windows export docs under code signing; skip it today.

Dodger.exe starts from Explorer, you can play a full round, and the best score is the same number the editor shows on the next F5. If the exe opens and immediately complains it cannot find the data: Dodger.pck is not in the same folder, or Embed Pck was on and you then moved only part of the output. If Export Project is greyed out: templates are missing or Export Path is empty. If you see a second exe such as a console wrapper: that comes from Debug > Export Console Wrapper. Launch Dodger.exe.

Debug export versus release export

Export With Debug picks which template is copied into the exe. Unchecked (what you just did) is a release export: smaller, no editor, no remote debugger. OS.is_debug_build() is false in that binary. Checked is a debug export: the debug template, which can talk to the editor's debugger. OS.is_debug_build() is true for a debug export and also while you press F5. The Android export page uses the same checkbox and tells you to leave it unchecked for a build you ship. Release is the file you would zip and send to someone.

  1. Export once with the checkbox on. Project > Export..., select Windows Desktop, tick Export With Debug, and click Export Project. Save as C:\GodotProjects\g01-dodger-export\Dodger-debug.exe so you do not overwrite the release exe. Untick Export With Debug again before you close the dialog, so the next export is a release.
  2. Compare. In Explorer, Dodger-debug.exe is larger than Dodger.exe. Run Dodger-debug.exe: the game plays the same. The difference is the binary (debugger present), not your scenes. You can delete Dodger-debug.exe and its pck afterwards; keep the release pair.
  3. The same switch exists on the command line. The export docs use --export-release and --export-debug. The preset must already exist. The output path is relative to the project, or absolute; it ignores the folder your shell happens to be in. From PowerShell, quoting the preset name because it contains a space: 
    godot --path C:\GodotProjects\g01-dodger --export-release "Windows Desktop" C:\GodotProjects\g01-dodger-export\Dodger.exe
godot --path C:\GodotProjects\g01-dodger --export-debug "Windows Desktop" C:\GodotProjects\g01-dodger-export\Dodger-debug.exe
    godot here means the editor executable (the same one you start the editor with). You do not need to run this if the dialog export already worked.

One file instead of two (Embed PCK)

  1. Turn embedding on. Project > Export..., select the preset, tick Binary Format > Embed Pck, leave Export With Debug unchecked, and Export Project to C:\GodotProjects\g01-dodger-export\Dodger-single.exe.
  2. Check the folder. There is no Dodger-single.pck. Double-click Dodger-single.exe. It plays, and the best score is still the one in user://, because embedding changes where res:// is packed, not where user:// lives.
  3. Put the preset back. Untick Embed Pck and set Export Path back to C:\GodotProjects\g01-dodger-export\Dodger.exe. The two-file release is the one the official "finishing up" page tells you to zip (the exe and the pck, not the project folder). Save happens when you export or close the dialog; export_presets.cfg appears in the project and is safe to keep.

You have a release Dodger.exe plus Dodger.pck that runs from Explorer, a debug exe you can tell apart by size, and a single-file exe from Embed Pck that also runs. Export With Debug is unchecked and Embed Pck is unchecked in the preset you left behind. If the single-file exe is missing resources: you exported with Export PCK/ZIP instead of Export Project.

Block 6: Portrait-window preview

The game is already a tall 480×720 window (Day 3): stretch mode canvas_items, aspect keep. keep means the 2:3 picture is scaled to fit and the engine adds black bars rather than squashing the art. On a wide window those bars are on the left and right (pillarboxing); on a window taller than 2:3 they are on the top and bottom (letterboxing). The HUD stays on the screen edges because its bars use anchor presets, and it does not shake with the world because it is a CanvasLayer.

  1. Run and resize. Press F5. The window opens taller than it is wide. Drag an edge until the window is much wider than 2:3. Black bars appear on the sides. The creeps and the score do not stretch. Drag it back, or close it with F8.
  2. Use the Game workspace size menu. In the Workspace buttons click Game, then press F5 if the game is not already running. The Game bar has a size menu on the right. Fixed Size uses the 480×720 viewport (or the window-size override below, if both overrides are greater than 0). Keep Aspect Ratio fills the area you give it but stays 2:3, so you still see bars. Stretch to Fit may change the aspect; that option only affects this embedded preview, not Project Settings.
  3. Optional phone-sized override. Project > Project Settings... > Display > Window > Size. Set Window Width Override to 390 and Window Height Override to 844 (both must be above 0 or Fixed Size ignores them). Run again: a narrower portrait window, still 2:3 inside the bars if the window shape does not match. Set both overrides back to 0 before you stop, so the next F5 is 480×720 again. The indigo rectangle in the 2D viewport is the viewport size, not the override.
Godot older than 4.4

The Game workspace and its size menu exist since 4.4. On 4.3, skip step 2 and only resize the floating game window. Stretch mode and aspect still behave the same way.

A wide window shows side bars, the play field stays portrait, and the score stays in the top corners. After the optional override test, both window overrides are 0 again. If the art stretches instead of showing bars: Display > Window > Stretch > Aspect is not keep, or the Game bar is on Stretch to Fit.

Common pitfalls

  • Export Project stays disabled. Templates are not installed, or they are for a different Godot version than the editor. Re-open Editor > Manage Export Templates... and match the version.
  • The exe starts and cannot find the game. Embed Pck is off and Dodger.pck is not in the same folder as Dodger.exe. Send both, or export again with Embed Pck on and send only that exe.
  • You shipped a debug build by accident. Export With Debug was still ticked, so the exe is the larger debug template. Untick it and export again. The game looks the same; the binary is what changes.
  • The export landed inside the project. Godot then imports Dodger.exe as a resource and the FileSystem dock shows a mess. Delete those imported files and export to C:\GodotProjects\g01-dodger-export.
  • The best score "disappeared" after a rename. user:// follows application/config/name. Changing the project name points user:// at a new folder. The old dodger.cfg is still under the old name in %APPDATA%\Godot\app_userdata.
  • Pause freezes the HUD too, or pauses nothing. The HUD's Process > Mode must be Always. If you set Main to Always, every child inherits it and Esc does not freeze the creeps. Children should stay Inherit.
  • A renamed node crashes the next run. $HUD, $Trail, %ScoreLabel and the rest are literal names. Unique-name access still needs Access as Unique Name on that node.
  • The file icon did not change. Modify Resources is off, or Windows is showing a cached icon. The game itself is fine. The icon page linked below mentions clearing the icon cache; do that only if you care about the logo on the exe.

Challenge (optional, 20-30 min)

An on-screen pause button

Esc is awkward on a tall phone window. Add a Pause button on the HUD that pauses and resumes the same way Esc does. Do not give the button its own copy of the pause rules.

  • Put the button under HUD, not under BottomBar. BottomBar is hidden while you play, so a pause control inside it would vanish at the moment you need it.
  • The HUD is already Always, so a button on it still receives clicks while get_tree().paused is true. A button parented under Main would not.
  • Connect pressed to a small function on HUD that calls the existing _toggle_pause(). You will need to allow that call from another function in the same script (it is already on HUD).
  • Show the button only while _game_active is true, and make the label switch between Pause and Resume from get_tree().paused.
  • Check three states: during play, while paused, and on the title screen (hidden or ignored).

Check yourself

With Binary Format > Embed Pck off, what does Export Project write, and what has to travel with the exe?

  • Only Dodger.exe, with the project stored inside it
  • Dodger.exe and a sibling Dodger.pck; the pck must stay in the same folder
  • A zip of the whole g01-dodger project folder
  • Only a pck, which Windows runs by itself

Export Project writes the runtime and the resource pack. Embed Pck off keeps the pack as its own file, named from the exe. Export PCK/ZIP would write the pack alone, which is not a game you can double-click.

You export with Export With Debug unchecked. Which statement matches the docs?

  • The exe refuses to run unless the editor is open
  • print() is stripped, so the Output panel is the only way to see logs
  • This is a release export: no remote debugger, and OS.is_debug_build() is false in that binary
  • user:// becomes read-only

OS.is_debug_build() is true for a debug template and for the editor, and false for a release template. Export With Debug selects the template. user:// stays writable either way.

The camera shake moves Camera2D.offset, but the score text does not shake. Why?

  • The HUD is a CanvasLayer, and that layer is not moved by the Camera2D
  • Labels ignore their parent's transform
  • get_tree().paused is true during the shake
  • The score label's anchor preset locks it to the camera

A CanvasLayer draws on its own canvas. Anchors pin the HUD to the screen edges; they are not what separates it from the shake. Pause is a different feature.

Where does HighScore store the best score, and why does the exported exe see the same number?

  • res://dodger.cfg, because an export can still write into the project
  • Inside Dodger.pck, rewritten every time you die
  • In an autoload that only exists in the editor
  • user://dodger.cfg, which on Windows is %APPDATA%\Godot\app_userdata\g01-dodger for both the editor and the exe, because both use the project name

res:// is read-only in an export. HighScore is a class_name with static functions, not an autoload. user:// follows application/config/name (g01-dodger), not the Windows product name.

Esc freezes the creeps, the timers and the music, but a second Esc still unpauses. What makes that possible?

  • ui_cancel is delivered only to CanvasLayer nodes
  • The HUD's process mode is Always, and the game nodes stay Pausable through Inherit
  • get_tree().paused pauses timers only, so the HUD was never going to stop
  • The pause logic lives in an autoload, which cannot be paused

Pausing stops nodes whose mode resolves to Pausable. The HUD is set to Always so it keeps reading ui_cancel. Setting Main to Always would be inherited by the creeps and they would not freeze.
