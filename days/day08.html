Concepts you need first

The shape of a tower defense

Before any clicking, here is the whole machine for Bastion Defense. Data lives in Resources, behaviour lives in a handful of small scenes, and a few signals glue them together.

DATA (Resource files, edited in the Inspector)
  EnemyData ---------------------------+
  WaveGroup (enemy, count, interval, delay)  |
  WaveData  (groups, health_scale, prep, bonus) |
  LevelData (waves[])                  |
                                       v
RUNTIME                         WaveSpawner --spawns--> Enemy (PathFollow2D) walking a Path2D
                                    |                        |  died(enemy)   reached_end(enemy)
                                    |  wave_started          v
                                    |  wave_cleared      Game (autoload: gold, lives, wave)
                                    |  all_waves_cleared     |  gold_changed, lives_changed ...
                                    v                        v
                                  Main (glue) ---------->  HUD, Base

Rule of thumb for this course: scenes own behaviour, Resources own numbers, signals carry events up, calls go down. The enemy never touches the HUD, the HUD never touches the enemy; both talk to Game or to signals.

Custom Resources are your ScriptableObjects

A Resource is a data object that Godot can save as a .tres text file, edit in the Inspector and share by reference. If you know Unity's ScriptableObjects or Unreal's Data Assets, it is the same idea. Give the script a class_name and it shows up in the editor's Create New Resource dialog; every @export variable becomes an Inspector field.

Shared by reference

Every enemy of a type points at the same EnemyData object in memory. Reading it is perfect. Never write to it at runtime (data.max_health -= 5 would change every grunt, forever). Per-enemy state (current health, slow timer) lives on the enemy node. Tonight's spawner passes a per-wave health_scale as a separate number for exactly this reason.

Path2D + PathFollow2D

Path2D holds a Curve2D (a list of points with optional Bezier handles). A PathFollow2D is a child of the path that places itself at a distance along the curve. You advance its progress (pixels along the curve) or progress_ratio (0.0 to 1.0) and it moves, optionally rotating to face the direction of travel. Two defaults bite beginners: loop is true (the follower wraps to the start instead of stopping) and rotates is true (the follower turns, which would spin our health bar). Our enemy script turns both off.

The curve is baked: Godot samples it into evenly spaced points every bake_interval pixels (default 5.0) and interpolates between them. A smaller interval follows tight Bezier curves more exactly and uses more memory; a larger one is cheaper and cuts corners. Our route has straight segments and sharp corners, so the default is already overkill.

Decision: fixed Path2D now, NavigationAgent2D as an option

Path2D + PathFollow2D (we use this)NavigationRegion2D + NavigationAgent2D
RouteOne hand-drawn curve per lane. Enemies cannot leave it.Any position inside a walkable polygon. The route is computed (A*-style) at runtime.
Best forClassic lane TD (Bloons, Kingdom Rush): the player decides where to shoot, not where enemies walk.Maze-building TD (Desktop TD, Gem TD): towers are walls and the player shapes the route.

Bastion Defense is a fixed-route game, so Path2D gives us simpler code, exact "first/last" targeting tomorrow and a flyer lane for free (a second, straight Path2D). You will find an optional, clearly marked navigation callout at the end of Block 3 with a working snippet.

Timers and await in a spawner

A wave is a script with waiting in it: "wait 8 seconds, spawn 5 grunts one per 1.2 s, wait until they are all gone". In GDScript you write exactly that with await get_tree().create_timer(1.2).timeout. One argument matters a lot here: create_timer(time_sec, process_always = true, ...). The default true means the timer keeps running while the game is paused. We pass false so pausing the tree also pauses our waves. The timer does respect Engine.time_scale (tomorrow's 2x speed button) unless you pass ignore_time_scale = true.

Tile custom data

A TileSet can carry custom data layers: extra named, typed fields attached to every tile (here a bool called buildable). At runtime tile_map_layer.get_cell_tile_data(cell).get_custom_data("buildable") returns it. That lets level art decide gameplay rules: paint grass and you can build there, paint path or rock and you cannot. No hard-coded cell lists.

You will draw two curves: GroundPath (the winding route) and AirPath (a straight diagonal for flyers, built the same way). All points sit on the centres of path tiles, which are odd multiples of 36 px, so a 36 px grid snap lands on them exactly.

P0(-36, 180)half a tile left of the screen, row 2 (spawn point, off-screen)
P1(252, 180)cell (3, 2), the first corner
P2(252, 396)cell (3, 5)
P3(540, 396)cell (7, 5)
P4(540, 108)cell (7, 1)
P5(828, 108)cell (11, 1)
P6(828, 468)cell (11, 6)
P7(1044, 468)cell (14, 6), the base

Cell centre formula: x = 36 + 72 × column, y = 36 + 72 × row. The ground curve is 1,944 px long, so a 60 px/s grunt needs about 32 seconds to cross it.

  1. Add a container. Select Main in the Scene dock, press Ctrl+A, create a Node2D and rename it Paths. (Enemies will become children of the path nodes, so it helps to keep them together and out of the way.)
  2. Add the ground path. Select Paths, press Ctrl+A, create a Path2D and rename it GroundPath. Do the same for a second Path2D named AirPath. Both stay at position (0, 0), so curve points are in world pixels.
  3. Turn on grid snapping. In the Viewport toolbar (top of the 2D viewport) click Use Grid Snap (the icon with a magnet next to dots). Then open the three-dot menu next to the snap buttons and choose Configure Snap.... Set Grid Offset to 0, 0 and Grid Step to 36, 36, then close the dialog. The Dodger tutorial used the same toggles to draw its spawn path.
  4. Select the path and pick the Add Point tool. Click GroundPath in the Scene dock. New buttons appear in the Viewport toolbar: Select Points, Add Point, Delete Point, Close Curve and an Options menu. Click Add Point (the "+" icon).
  5. Click the eight points in order. Click P0 at the left of the screen, half a tile outside the blue project rectangle, vertically in the middle of the third tile row. Then P1 in the middle of the first corner tile, P2, P3 … up to P7 in the middle of the tile where the path ends. Use the table above and the painted sand tiles as your guide; the 36 px snap pulls each click onto the exact centre. A line connects the points as you go. Do not click Close Curve: the route must not loop back.
  6. Fix mistakes. Press Ctrl+Z to undo a bad point. To move one, click Select Points and drag it. To remove one, click Delete Point and click the point (right-click on a point in Select mode also deletes it). With Add Point active, clicking on the line between two points inserts a new point there. Dragging with Shift held from a point pulls out a Bezier handle; we keep straight segments, so avoid that.
  7. Look at the bake interval. With GroundPath selected, click the Curve value in the Inspector to unfold the Curve2D resource. Bake Interval (bake_interval) is 5 px. Leave it. Rule of thumb: for curvy Bezier paths use 5-10; raising it to 50 would make sample_baked() (tomorrow's aim prediction) cut corners.
  8. Draw the air path. Select AirPath, keep Add Point active and click two points: P0 again at (-36, 180) and then the base tile centre at (1044, 468). You get a straight diagonal across the map. Flyers will take this shortcut.

Probe a PathFollow2D

  1. Add a probe. Right-click GroundPath in the Scene dock, choose Add Child Node, create a PathFollow2D and rename it Probe. With Probe selected press Ctrl+A and add a Marker2D child so there is something visible (a cross in the editor).
  2. Move it along the curve. Select Probe. In the Inspector find Progress Ratio (progress_ratio) and type 0.5. Select GroundPath and the Viewport shows a line through the middle of every sand tile, with eight small point handles, starting off-screen left and ending on the tile at (14, 6). Select AirPath: one straight diagonal. If a segment cuts diagonally across the grass, a point snapped to the wrong grid cell: switch to Select Points and drag it to the centre of the correct tile. Optional: maze-building tower defense with NavigationAgent2D

Everything in this callout is optional and not used by Bastion Defense. Read it so you know where the road forks.

In a maze TD towers are walls, so the route is not fixed and must be recomputed. The pieces (see the 2D navigation overview): a walkable area as a navigation mesh, an agent per enemy that asks the NavigationServer2D for the next path point, and code that moves the enemy. With tiles, the usual setup is: add a Navigation Layer to the TileSet, give each walkable tile a navigation polygon (same polygon editor as collision), tick Navigation Enabled on the TileMapLayer, and "build" a tower by replacing the floor tile with a tile that has no polygon. Then every enemy re-targets the goal. Two traps: the navigation map synchronizes on the next physics frame (await get_tree().physics_frame before querying), and you must reject any placement that would seal the goal (ask NavigationServer2D.map_get_path() for a path from spawn to goal and refuse if it does not end at the goal). Verify the details in the class reference before building on them.

Why the health bar is drawn in code

A ProgressBar works but is a Control: layout, a theme with two StyleBoxFlat overrides and an extra node per enemy. A TextureProgressBar needs two textures (you can make them with GradientTexture2D). _draw() costs zero extra nodes and gives full control; with 60 enemies on screen that matters. The bar only appears once an enemy is damaged, which also keeps the screen readable.

Common pitfalls

  • Writing into grunt.tres at runtime. Every grunt shares one EnemyData. Change health on the enemy node. The per-wave knob is health_scale, passed in before add_child.
  • create_timer keeps running while paused. The default of process_always is true. Pass false, or the game-over pause still spawns the rest of the wave. Leave ignore_time_scale at its default false so tomorrow's 2× button speeds the spawner too.
  • The follower wraps the path. PathFollow2D.loop defaults to true. enemy.gd sets loop = false and rotates = false. If a grunt orbits forever, that script is not the one on the scene.
  • Restart resets Game too early. reload_current_scene swaps the scene at the end of the frame. The old spawner must still see Game.ended. Main._ready is what calls Game.reset() on the new scene.
  • The HUD eats the pause. A CanvasLayer on the default process mode freezes with the tree, and the Restart button never receives the click. Mode must be Always.
  • Autoload name mismatch. The global is Game because that is the Node Name in Globals > Autoload, not because of the file name.
  • Expecting towers to bend the route. Enemies are welded to GroundPath or AirPath. Blocking a sand tile does nothing. The maze alternative is the optional NavigationAgent2D callout in Block 3, and it is not wired into this project.

Check yourself

Why does the spawner call create_timer(seconds, false)?

  • The timer ignores Engine.time_scale.
  • The timer pauses when the scene tree is paused.
  • The timer repeats forever until you call stop().

false is process_always. The default true would keep spawning during game over. Time scale is a different argument and stays at the default, so a future 2× button still speeds the wave.

You run grunt.tres's resource and, in code, set data.max_health = 1 on a living enemy. What happens?

  • Only that one node has 1 health.
  • Every current and future grunt reads 1 health, because they share the resource.
  • Godot refuses the write and prints an error.

A .tres loaded once is one object. Per-enemy health lives on the Enemy node. The wave's health_scale is a separate number so the file stays untouched.

Which PathFollow2D defaults does enemy.gd turn off, and why?

  • loop and rotates, so the enemy stops at the base and the health bar stays upright.
  • Only loop. Rotation is already off.
  • Neither. Both already default to false.

Both properties default to true. Left alone, the enemy wraps to the start after the base, and the drawn health bar spins with the curve.

An enemy dies on the path. Who updates the gold readout?

  • The enemy writes GoldLabel.text itself.
  • The spawner calls Game.add_gold, and the HUD updates on gold_changed.
  • The tile's buildable custom data stores the gold.

Scenes own behaviour, the autoload owns the numbers, signals go up. The enemy only emits died. It never mentions the HUD.

The grunt's progress_ratio hits 1. Which signal is that?

  • died, and the player is paid the reward.
  • reached_end, and the player loses damage_to_base lives.
  • all_waves_cleared, immediately.

died is only for take_damage reducing health to 0. Reaching the base is reached_end. The victory signal waits until every wave has spawned and _alive is empty.
