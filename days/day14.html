Concepts you need first

A breakpoint is a pause you asked for

The Debugger bottom panel is not the Output panel. Output shows print and errors while the game keeps running. The debugger stops the process. A red dot in the script gutter is an editor breakpoint. It survives editor restarts even if you forgot to save. The breakpoint keyword is a line of GDScript, so it travels with the file and would ship if you leave it in. Today you will use both, and you will delete both before the git commit.

While stopped, the Stack Trace tab shows the call stack and the locals. The Evaluator tab is a small expression box for the same paused frame. Continue, Step Over, and Step Into sit in the debugger toolbar. Step Into enters a function call. Step Over runs the line and stays in the current function.

Remote is the running tree

With the game running from the editor, the Scene dock gains Remote and Local. Remote is the live tree. Changing a property there changes the running game and is thrown away when you stop. Local is the scene on disk. The overview of debugging tools is explicit about this split. Do not edit gameplay on Remote and expect Ctrl+S to keep it.

Two profilers, plus monitors

The Profiler tab measures frame time, physics time, and idle time, including your scripts. It stays off until you press Start, because measuring has a cost. Frame time includes rendering. Physics time is _physics_process and physics nodes. Idle time is _process and idle timers. The reference frame at 60 physics ticks per second is 16.66 ms. The Visual Profiler is only the CPU time spent on rendering tasks. It does not include script or physics. Monitors are the running graphs (FPS, memory, node count). They keep history even if the tab was closed during play, so you can open them afterwards. Video RAM lists resources by path.

Block 2: Debugger exercises on the dungeon

Stay in g05-torchlight-dungeon. These steps add a stop, prove you can see data, then remove the stop. The game you commit must not contain a breakpoint.

  1. Gutter breakpoint. Open res://enemies/enemy.gd. Find the line velocity.x = dir.x * SPEED inside _chase. Click the gutter immediately left of the line number. A red dot appears. Hovering the gutter first shows a faint dot. Clicking makes it solid. That dot is stored by the editor, not by the file.
  2. Hit it. Press F5. Walk toward EnemyA until it can see you. The game freezes. The bottom panel switches to Debugger, tab Stack Trace. A green arrow sits on that line in the script editor.
  3. Read the stack. In Stack Trace, select the top frame (_chase). In the variables tree, find dir and SPEED. SPEED should be 2.6. dir is a Vector3 whose Y is 0. If the tree is empty, you selected a frame above the script. Click the frame whose file is enemy.gd.
  4. Evaluator. Open the Evaluator tab in the Debugger panel. The docs describe it as a REPL that runs while the process is interrupted. Type global_position and confirm. You should see a position near EnemyA, around (7, 1, 7) if you have not led it far. Type SPEED * 2.0. The result is 5.2. Evaluator expressions use Godot's expression language, so do not paste a whole function.
  5. Step and continue. Press Step Over once. The green arrow moves to the next line. Press Continue. The enemy walks again. It will hit the same breakpoint on the next physics frame. Press Continue three more times so you believe it, then press F8 to stop the game. Leaving it broken and clicking around the editor is how you lose the panel.
  6. Remove the gutter dot. Click the red dot again so it disappears. Save nothing related to it. The file on disk did not change.
  7. Keyword breakpoint, then delete it. Open res://player/player.gd. Inside _fire, on the line after ammo_in_mag -= 1, add a line that is only the keyword:
  1. Fire once. Save the script. F5. Click the left mouse button. The debugger stops inside _fire. In Stack Trace, ammo_in_mag is 7 (it was 8, you already decremented). In Evaluator type ammo_reserve. It is 24 if you have not reloaded. Press Continue, then F8.
  2. Delete the keyword. Remove the breakpoint line. Save player.gd. Search the script editor with Ctrl+F for breakpoint. Zero hits in player.gd and enemy.gd. A keyword breakpoint is committed if you leave it, and the next person who runs the project stops on every shot.
  3. Errors tab. Open Debugger > Errors. It lists errors and warnings from the session. A clean run shows nothing new. The docs note that GDScript warning categories can be turned down under Project > Project Settings > Debug > GDScript. Leave those defaults. Hiding warnings is not a fix.
  4. Remote tree. F5 again and do not pause on a breakpoint. Click the game window, then click back on the editor. At the top of the Scene dock, click Remote. Expand the tree to Main/Player/Head/SpotLight3D. In the Inspector set Light Energy to 20. The torch in the game window flares. Click Local. The saved energy is still about 5, because the script overwrites it every frame anyway and Remote edits are not the scene file. Press F8.

Search both scripts for the word breakpoint and find none. The gutter on velocity.x = dir.x * SPEED has no red dot. F5, shoot once, and the game does not freeze. Remote is gone from the Scene dock after F8, which is normal: those tabs exist only while a session is running. If the game still stops, a second red dot is on another line. Check the script editor gutter from top to bottom.

Block 3: Profiler, Visual Profiler, monitors

  1. Start the script profiler. F5. Focus the editor. Bottom panel, Debugger, tab Profiler. Click Start. The profiler does not run by itself. Autostart exists and is not remembered across editor sessions. Leave it off so you do not pay the cost tomorrow without noticing.
  2. Play for twenty seconds. Click the game. Sprint, turn, shoot two rounds, open the pause menu, resume. Focus the editor and click Stop on the Profiler tab. Do not press F8 yet. Stopping the profiler keeps the capture. Stopping the game is the next step, after you have read the numbers.
  3. Read frame time. The graph's main rows are frame time, physics frame, idle time, and physics time. Physics frame is the budget, 16.66 ms when physics is 60 Hz. Frame time is the whole picture, rendering included. Click a tall spike on the graph. The left-hand list jumps to that frame. Scroll until you see script functions. You should find _physics_process on the player or the enemy if they ran that frame. Write the peak frame time, in milliseconds, into day14-triage.txt under a heading profiler.
  4. Clear is not required. The Clear button drops the capture. The Measure dropdown changes which series is drawn. Leave Measure on the default unless you are hunting one counter. Press F8 now.
  5. Visual Profiler. F5. Debugger > Visual Profiler. Click Start. Look around the dungeon for about ten seconds, including a pause. Click Stop. The categories are rendering tasks. The docs are blunt: this tab does not include scripting or physics. A slow _physics_process will not show up here. That is what the previous tab was for. On Forward+, shadow-casting lights show up as real categories. You have one shadowed SpotLight3D. Write one category name you actually see into the note. Press F8.
  6. Monitors after the fact. Run F5, play for ten seconds, press F8. Then open Debugger > Monitors. The graphs still have data. The debugger page says monitors keep history even if the tab was not visible during play. Find FPS and the node or object count. Write the FPS number into the note. If the graph is flat at the top, click it and read the scale rather than guessing.
  7. Video RAM. With a session just finished, or during a new F5, open Debugger > Video RAM. The list is resources by path: meshes, materials, viewport textures. The total sits at the top right of that tab. Confirm mesh_library or a BoxMesh path appears. Press F8 if the game is still running.
What to ignore on a dungeon this small

The 3D performance page talks about occlusion culling, transparency sort cost, and mesh LOD. Your GridMap is a handful of opaque boxes. Automatic instancing on Forward+ already batches MeshInstance3D nodes that share a mesh and an opaque material, which is why the library materials had to live on the mesh resource. You do not add occluders today. You do turn an extra shadow off if a later level grows: the torch is the only shadow-casting light on purpose.

The note contains a frame-time number, one Visual Profiler category, and an FPS number. The dungeon still reaches the first room with F5. If the Profiler list stays empty, Start was clicked before the game was running, or you pressed Clear. Run, then Start, then play, then Stop.

Block 4: Rules you are keeping, then git

These are the best-practice pages, applied to the games you already built. Read them as decisions, not as new systems to code.

  1. Scenes own their nodes. The scene organization page wants a scene to carry what it needs, and to take outside information from its parent. The enemy scene owns its mesh, its agent, and its Health child. main.gd does not reach into the capsule to invent a second health variable. Dodger's mob scene and the tower scene in Bastion are the same shape. If a script starts with a chain of get_parent().get_parent(), the scene is borrowing a job that belongs higher up, or the parent should have passed a reference.
  2. Autoloads are for wide scope, and you have used none. The autoload page's warning is global state: one object that every scene can break. A class_name such as Health shares behavior without a singleton. Static functions share helpers that do not need per-instance data. The dungeon keeps the key list on Main, the scene root, which is the "owner" option that page describes. Part 2 adds five autoloads because settings, saves, and scene changes outlive a single scene. Their names are Events, Settings, SaveManager, Audio, and SceneRouter, in that order. You will not create them today.
  3. Prefer the node that already does the job. RayCast3D for a beam you want to see in the editor. intersect_ray for a shot that exists for one physics frame. NavigationAgent3D instead of a hand-rolled grid search on a map that already has a NavigationMesh. AudioStreamPlayer on the player for footsteps, not a project-wide sound singleton, for the reason the autoload page uses a coin sound as its example.
  4. One folder per concern. player, enemies, props, ui, components, library. The project organization guidance is the same idea as the Ship Kit folders you will see on Day 15. Do not start a scripts folder that mixes all of them.
  5. Data that must survive a restart is a file, and JSON floats are floats. Best time is user://torchlight_best.json. You already cast with int() on load. ConfigFile, which Dodger can use for a high score, does not have that particular trap. Pick one format per game and stick to it.
  6. Generate ignore files before the first commit. Stay in the dungeon project. Menu bar: Project > Version Control > Generate Version Control Metadata. Godot writes .gitignore and .gitattributes in the project root. The version-control page says this is the same pair the Project Manager writes when you pick Git at creation. If you already chose Git on Day 12, the files exist and the menu is a harmless no-op or a confirm. Keep them. They exclude .godot/, which is cache, and imported translation binaries.
  7. Commit with PowerShell. Close any running game (F8). In a terminal:
External resource (not in the Godot docs)

If PowerShell says git is not recognized, install Git for Windows from https://git-scm.com and open a new terminal. Verify the steps on that site. Installers change. If git commit refuses because a name and email are unset, follow the message Git prints. This course does not walk through global git settings.

Line endings

The version-control docs discuss Windows clients rewriting LF to CRLF and marking files dirty. The generated .gitattributes is the project's answer. Do not "fix" dirty files by deleting .godot from disk while the editor is open. That folder is a cache the editor rebuilds.

git status after the commit prints a clean working tree, or only files you chose not to add. git status before the commit must not list .godot/ as a new folder. If it does, .gitignore is missing. Run the Version Control menu again, then git status. Also search the project for breakpoint one last time. A clean commit that freezes on every shot is not clean.

Common pitfalls

  • Editing on Remote and saving Local. They are different trees. A light energy you typed while Remote was selected dies with the session.
  • Leaving breakpoint in _fire. Gutter dots are editor state. The keyword is source. The git commit will publish the keyword.
  • Judging scripts from the Visual Profiler. That tab is draw-call CPU time. Script cost is the Profiler tab, under script functions, after you click a frame.
  • Autostart left on. The checkbox is session-only, but within the session every F5 pays the profiler cost and the game feels worse than it is.
  • Committing .godot. It is large, it changes every import, and the official ignore list starts with it.
  • Using today to restart a game from Day 3. Triage records the gap. It does not schedule an eight-hour rebuild. Part 2 has its own projects.

Check yourself

A red dot in the script gutter and a breakpoint line differ because:

  • Only the keyword can stop the game
  • The keyword is saved in the script and will be committed. The gutter dot is editor state
  • The gutter dot only works on _process
  • The keyword is removed automatically when you press Continue

The debugging overview says gutter breakpoints persist in the editor even across restarts, and the keyword persists in the file, including across machines in version control.

You changed SpotLight3D energy while the Scene dock said Remote. After F8, Local still shows the old value. What happened?

  • Remote edits the running process. They are not written to the scene file
  • Forward+ ignores Inspector edits
  • Energy is read-only while volumetric fog is on
  • You edited the MeshLibrary by accident

The overview calls Remote the place to inspect or change parameters in the running project. Local is the saved scene. The torch script also writes energy every frame, so a Remote value would flicker even during the session.

Frame time on the Profiler is high, but physics time and the script list look cheap. Where does the profiler page tell you to look next?

  • A missing .gitignore
  • The Input Map
  • Rendering. Frame time includes it. Particles and visual effects are the example the page gives
  • The autoload list, which is empty

The profiler docs say frame time includes rendering, and a spike with fast scripts can be a visual effect. The Visual Profiler is the follow-up for draw-call cost, and it still will not show GDScript time.

Why does this course keep Health as a child node with class_name, instead of an autoload named HealthManager?

  • Autoloads cannot hold integers
  • class_name is required for every script
  • GridMap deletes autoloads
  • The autoload page treats global access as a way to make every bug the whole project's bug. A child Health stays with the body that owns it

Shared behavior can be a class_name without a singleton. Autoloads fit systems that outlive one scene and manage their own data. Part 2's five autoloads are that case. A hit point total is not.

Which path does the version-control page tell you to keep out of git?

  • project.godot
  • .godot/
  • player.gd
  • user://torchlight_best.json

.godot/ is the editor cache. project.godot is the project and should be committed. The best-time file is under user://, outside the project folder, so git in the project root never saw it.
