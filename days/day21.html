Concepts you need first

A node is the expensive part

Day 19's pool capped the swarm at 36 because each enemy was a node, a sprite, and a collision shape. A thousand of those is a thousand entries in the scene tree and a thousand canvas items the scene system has to visit. The draw itself is cheap. The per-node bookkeeping is not.

A canvas item is the thing the renderer actually draws. Sprite2D owns one. You can also create one with RenderingServer.canvas_item_create(), parent it with canvas_item_set_parent, and draw into it with canvas_item_add_circle or canvas_item_add_rect. Those draw commands are baked. You cannot edit a circle's radius in place. You canvas_item_clear and add it again. The transform is the exception: canvas_item_set_transform can run every frame. That split is the whole trick. Create the circle once. Move it forever.

From the servers tutorial

Keep any texture you pass in alive for as long as the RID needs it (a local variable that dies at the end of _ready is not enough). Call canvas_item_reset_physics_interpolation the frame you first place the item, or it can glide in from the origin. Call free_rid when you are finished, including in _exit_tree. This day uses circles, so there is no texture to retain.

The other tool, not the one you build

MultiMeshInstance2D draws many copies of one mesh in one go. You would set transform_format = MultiMesh.TRANSFORM_2D, set use_colors = true before instance_count (the class reference rejects that flag once the count is non-zero, unless you set the count back to 0), assign a QuadMesh whose size is the sprite size, then each frame call set_instance_transform_2d and, if you need tints, set_instance_color. visible_instance_count limits how many of those instances draw. It is excellent when every enemy is the same quad. Two radii want two meshes. Per-item show and hide is clumsier than a canvas item's visibility flag. Circles also need no mesh asset. That is why the swarm below is canvas items. Both approaches work on every renderer.

Block 4: Profile it

  1. Stress toggle. Select Game in game.tscn. In the Inspector, turn on Stress Spawn. This skips weapons and contact and spawns every 0.02 s, up to 1100. It exists so you can see the horde without waiting for a 15-minute run. Turn it off again before the export steps. Save the scene after you turn it off; a saved true would ship.
  2. Monitors. Press F6, click Start, then click the editor to focus it. Bottom panel, Debugger, then Monitors. Watch FPS, Process, Physics Process, Object Count (nodes), and Draw Calls. Also tick BH/Alive. Let the alive count pass 1000. Object Count must stay within about 30 of the BH nodes number printed at launch. A thousand enemies did not add a thousand nodes.
  3. Script profiler. Still in Debugger, open Profiler. Click Start. Return to the game for about ten seconds. Click Stop. Click the graph to pick a heavy frame. In the function list, find horde.gd _physics_process. That function is allowed to be the hot one. Frame time on the graph is the whole frame. The budget you are aiming at on this desktop is 16.6 ms, which is 60 frames per second. If you are over it, the list tells you whether the cost is the horde loop or something else (a stray enemy scene you are still instancing, for example).
  4. Visual Profiler. Debugger, Visual Profiler, Start, play a few seconds, Stop. This measures CPU time spent submitting the 2D canvas, on every renderer including Mobile. It does not measure GPU time. Write down the number. You are looking for a spike that appears only when the alive count jumps, which would mean the canvas submission, not your GDScript, is the wall.
Version note

The docs page for the ObjectDB Profiler says it exists since Godot 4.6, as a Debugger tab. If your build has that tab, you can confirm the horde is not leaking nodes when you stop the stress run. If the tab is missing, skip it. Monitors and the script profiler are enough.

With Stress Spawn on, BH/Alive crosses 1000 and Object Count does not. Turn Stress Spawn off, save, and press F6 again. Weapons fire. You can die. A normal minute does not spawn a thousand bats, and it should not.

Common pitfalls

  • Enemies appear at the wrong place or slide in from the corner. You skipped canvas_item_reset_physics_interpolation on spawn, or Horde is not at the origin. The docs call the interpolation reset out specifically for server-created canvas items.
  • You canvas_item_clear inside _physics_process. That rebuilds 1000 draw lists a frame and the profiler will show it. Clear only when the kind stored on that slot changes.
  • RIDs leak after you stop the game from the editor. free_rid belongs in _exit_tree. Hot-reloading the script while the game runs can skip that. Stop with F8 and run again.
  • Object Count climbed. Something is still instancing enemy.tscn. Search for ENEMY_SCENE. The Day 21 director does not preload it.
  • JSON turned the coin balance into a float. Every read uses int(SaveManager.get_value(...)) before math. A missing int() makes 1 << rank fail or makes the shop price a float comparison that looks random.
  • Stress Spawn shipped. The Inspector checkbox is saved in the scene. Export after you turn it off and save.
  • Boss shots use apply_contact. That function treats the number as HP per second. hurt(14) is 14 HP once. Mixing them up deletes the player in one frame or tickles them.

Check yourself

You want a living bat to move 3 pixels. What do you call?

  • canvas_item_clear, then canvas_item_add_circle at the new position.
  • canvas_item_set_transform with a Transform2D whose origin is the new position.
  • queue_free on the RID.
  • MultiMesh.visible_instance_count.

Draw commands are immutable. The transform is not. Clearing every frame throws away the reason you used canvas items.

When must use_colors be set on a MultiMesh?

  • After instance_count, or the colors are ignored.
  • Only on a MultiMeshInstance3D.
  • Before instance_count is greater than zero. Otherwise set the count back to 0, set the flag, then set the count again.
  • It is implied by TRANSFORM_2D.

The class reference says use_colors can only be set while instance_count is 0. This day does not build the MultiMesh path, but that order is the usual footgun.

Why does BH/Alive at 1000 not add about 1000 to Object Count?

  • Those enemies are RIDs owned by one Horde node, not nodes in the tree.
  • Object Count ignores Node2D.
  • The Mobile renderer hides nodes from the monitor.
  • free_rid deletes nodes.

Object Count is nodes. The horde holds positions in packed arrays and canvas items in an Array[RID]. Shots and gems are still nodes, and their pools were created up front.

A shop rank is 3 and the base price is 200. What does the next purchase cost?

  • 203
  • 600
  • 800
  • 1600

shop_cost(200, 3) = 200 × 2^3 = 1600. Rank 0 costs the base. Rank 5 is not for sale.
